# Rust Packaging

## When to Load

Load when the spec uses `%cargo_*` macros, `%{crates_source}`, BuildRequires
`cargo-rpm-macros` (or the older `rust-packaging`), the package is named
`rust-*`, or the sources contain `Cargo.toml`.

Reference: https://docs.fedoraproject.org/en-US/packaging-guidelines/Rust/

## Package Types

| Type | Name | Contents |
|------|------|----------|
| Library crate | `rust-<crate>` | Only `-devel` subpackages carrying crate sources under `%{crate_instdir}`; noarch |
| Binary crate | `rust-<crate>`, binaries in a `<crate>` subpackage (may be renamed) | Compiled binaries; arch-specific |
| Compat crate | `rust-<crate><major>` (e.g. `rust-nom7`) | Older semver-incompatible version kept alongside the current one |
| Project not packaged from crates.io (application, cargo workspace, Python package written in Rust) | upstream project name, never `rust-` | Built from the upstream release tarball, against system or vendored crates |

Only packages built from crates.io sources take the `rust-` prefix; the
guidelines require it for crates and forbid it for everything else. A
project packaged as a whole from its upstream tarball is named after the
project: the sandogasa cargo workspace is packaged from its GitHub
release tarball as `sandogasa`, and there is no `rust-sandogasa`. Such a
package must not ship crate sources in `%{cargo_registry}` (no `-devel`
crate subpackages, no `crate(...)` provides), and should not use
`%{crates_source}`, even if some of its crates are also on crates.io.

Library crates produce one `rust-<crate>-devel` subpackage plus one
`rust-<crate>+<feature>-devel` subpackage per cargo feature (including
`+default-devel`). These are generated by rust2rpm and map cargo features
to RPM dependencies via `crate(<name>/<feature>)` provides.

## Standard Spec Shape

```
%bcond check 1
%global crate foo

Name:           rust-foo
Version:        1.2.3
Release:        %autorelease
Summary:        ...
License:        MIT OR Apache-2.0
URL:            https://crates.io/crates/foo
Source:         %{crates_source}

BuildRequires:  cargo-rpm-macros >= 24

%prep
%autosetup -n %{crate}-%{version} -p1
%cargo_prep

%generate_buildrequires
%cargo_generate_buildrequires

%build
%cargo_build

%install
%cargo_install

%if %{with check}
%check
%cargo_test
%endif
```

Binary packages additionally collect dependency licenses:

```
%build
%cargo_build
%{cargo_license_summary}
%{cargo_license} > LICENSE.dependencies

%files
%license LICENSE LICENSE.dependencies
```

## Review Checks

- [ ] Spec is rust2rpm-generated or closely follows its output
- [ ] `%cargo_prep` is present (sets up offline cargo config pointing at
      system crate registry or vendored crates)
- [ ] `%cargo_generate_buildrequires` used, not hand-written crate
      BuildRequires (except for rare cases rust2rpm cannot express)
- [ ] For binaries: `License:` reflects the licenses of all statically linked
      crates, derived from `%{cargo_license_summary}`, and
      `LICENSE.dependencies` is shipped
- [ ] Changes to `Cargo.toml` (relaxed dependency bounds, dropped
      Windows/macOS-only deps, removed dev-dependencies) are done as a patch
      generated by `rust2rpm -p` / documented in `rust2rpm.toml`, with a
      comment explaining each change
- [ ] Library crates are noarch-equivalent (only `-devel` subpackages, no
      compiled output)
- [ ] Arch-specific packages use `ExclusiveArch: %{rust_arches}` only when
      needed (rust2rpm-generated binaries normally don't need it in current
      Fedora)
- [ ] Compat packages (`rust-foo0.3`) only exist when a dependent cannot be
      ported to the current version
- [ ] Vendored builds: vendor tarball is reproducible (documented generation
      command), `%cargo_prep -v <vendordir>`, `%cargo_vendor_manifest` used
      so `bundled(crate(...))` Provides are generated, licenses of vendored
      crates covered
- [ ] Skipped tests use `%cargo_test -- -- --skip <name>` (or
      `--exact`) with a comment explaining why, rather than disabling `%check`

## Security Advisories (RUSTSEC)

A RUSTSEC advisory's "patched" version may only deprecate the vulnerable
API rather than remove or fix it. Example: RUSTSEC-2026-0386 (tokio
`AsyncFd::new` and related constructors violate I/O safety, an
"unsound" advisory) counts tokio 1.53.3 and 1.54.1 as patched, but
their CHANGELOG entry is "io: deprecate
`AsyncFd::{new, with_interest, try_new, try_with_interest}`" plus new
safe `AsyncFd::register` / `register_with_interest`; the unsound
constructors are still there.
- Bumping to the patched version is still right, but it is not the
  whole mitigation: read the advisory and the fixed release's CHANGELOG
  for what actually changed
- Check whether anything still calls the deprecated API. In the
  package's own code, rustc's `deprecated` lint reports it (build with
  all features enabled). In dependencies it never does, because cargo
  caps lints for non-local crates (`--cap-lints allow`), so grep the
  vendored sources or `~/.cargo/registry/src` for the locked versions
- A deprecate-only fix may not be filed as a security update in Bodhi
  (the tokio updates were deliberately left with update type
  `unspecified`, not `security`), so don't wait for one: compare the
  advisory's patched versions with what is in stable

## Build Failures

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| `%generate_buildrequires` fails: `nothing provides crate(foo/default) >= 0.5` | Required crate version not packaged | Package/update the crate, or relax the bound in `Cargo.toml` via patch if the API is compatible, or package a compat crate |
| `failed to select a version for the requirement` during `%cargo_build` | Mismatch between `Cargo.toml` bounds and what is installed from the system registry | Same as above; check `Cargo.toml` patch is applied (it must be applied in `%prep` before `%cargo_prep`) |
| `no matching package named X found` / `failed to load source for dependency` | Optional or platform-specific dep (e.g. `winapi`) still referenced | Remove the dep from `Cargo.toml` in the rust2rpm patch |
| Build attempts network access to crates.io | `%cargo_prep` missing, or a `.cargo/config.toml` from upstream overrides the offline config | Add `%cargo_prep`; remove upstream cargo config in `%prep` |
| Tests fail only in mock | Tests need network, write to the source tree, or depend on specific environment | Skip the specific tests with `--skip` and a comment |
| Linking fails for `-sys` crate | Missing C library `-devel` BuildRequires, or the crate tries to build a bundled C copy | Add BuildRequires; ensure the system-library feature is used rather than vendored C sources |
| `Missing build-id` / empty debuginfo | Binary built with raw `cargo build` instead of `%cargo_build`, or custom release profile with `strip = true` | Use `%cargo_build`; patch out `strip`/`debug = false` profile settings |
| Build fails after Rust toolchain update | New lints set to deny in upstream (`#![deny(warnings)]`), or stabilization changes | Patch out `deny(warnings)`, backport upstream fix |
| i686/32-bit OOM during link | Large crates exhausting address space | Reduce codegen units/debuginfo level for that arch, or ExcludeArch with tracker bug |

## False Positives

- `rust-*-devel` and `rust-*+feature-devel` subpackages having near-empty
  `%files` (feature subpackages carry only dependencies via a ghost/empty
  file list): this is by design
- Library crate packages with no `%{_bindir}` content and noarch
  `-devel` subpackages: expected
- Missing explicit `Requires` on other crates: generated automatically from
  `Cargo.toml`
- `License:` on binary packages listing many licenses joined by `AND`:
  expected, reflects statically linked dependencies
- Patches named `<crate>-fix-metadata.diff` modifying only `Cargo.toml`:
  standard rust2rpm practice
- rpmlint `devel-file-in-non-devel-package` or `no-documentation` on crate
  source packages: crate layout requirements, not packaging errors
